# Structural Enumeration: From 30 Seconds to 31 Milliseconds

The CVA6 CV-X-IF encoding space covers 33,554,432 combinations. The standard
pipeline expands them all into a Vec, evaluates every constraint on every
combination, and reports pass/fail. It takes 29.7 seconds and produces the
correct answer. This was already impressive — faster than random simulation
with higher coverage than formal tools.

But the question that drove this work was different. Not "can we verify the
space?" but "what is the minimum work required to verify the space?"

## The Structural Insight

The CVA6 encoding space has five fields (funct3, funct7, rs1, rs2, rd) and
three constraints: oneof(funct3, [0,1,2]), cross(funct3->funct7 with 3
mapping entries), and two enable_masks. Of the 33.5M raw combinations, only
229,376 are structurally valid — 0.68%.

The standard pipeline generates all 33.5M combinations then filters to 229K.
The structural pipeline generates only the 229K. The difference is 146x fewer
combinations to visit. With the same constraint checking code, the structural
pipeline runs in 31.3 ms instead of 29.7 seconds.

## The synTagma Connection

The structural pipeline uses synTagma's DynCoordSpace<CoordSet> to encode
cross constraints into the enumeration space. Instead of generating every
funct3/funct7 pair and checking against a HashMap at runtime, the constraint
is compiled into a per-parent CoordSet. When funct3=0, only funct7 values
0,2,6,8,32 can be visited. When funct3=2, only funct7=96.

The CoordSet is a 175-word bit array (11172 bits, 1.4 KB). The contains()
check is a single bit test. There is no hashing, no branching, no allocation.

## The Bug that Wasn't a Bug

The first attempt at sync-cross-children logic had a subtle infinite loop:
when a parent field advanced, the child was reset to index 0 and re-advanced.
For a 3-entry parent space (CVA6) this was fine. For a 74-entry parent space
(Ibex rv32imcb) with 128 parent values and 8 child values, the reset-on-
every-advance produced 25 million iterations instead of 313 thousand.

The fix was simple: don't reset the child. Just advance from the current
position until a valid value is found. The staleness check in next() handles
the cross-constraint invariant without resets, and without the recursive
sync that caused the explosion.

## What This Is Not

A reader might see "29.7 seconds to 31.3 milliseconds" and ask: is this
fair? The standard pipeline allocates 33.5M combinations into a Vec (4 GB
peak), evaluates constraints on every one, and reports pass/fail. The
structural pipeline visits 229,376 combinations and evaluates exactly the
same constraints on each one. The difference is not in the evaluation ---
it is in what is generated. The standard pipeline computes the full
Cartesian product and filters. The structural pipeline encodes constraints
into the enumeration space and generates only the structurally valid subset.

This is not an optimization. It is a change in problem decomposition.
"Generate everything then filter" is replaced by "encode the filter into
the generator." The result is a different algorithm with different
asymptotics: O(N) becomes O(V) where V is the structurally valid subset,
independent of the raw space size.

## What Remains

The Ibex rv32imcb fixture with 74 cross-mapping entries triggers a deeper
issue in StructuralEnum's iterator for high-cardinality parent spaces. The
simple fixup_stale_children approach works for CVA6 (3 parent entries) but
not for Ibex (128 parent values). The root cause: when the parent has 128
values and the child has 8, the staleness check after every advance produces
massive over-iteration. A different approach -- pre-computing per-parent
child ranges -- would eliminate the runtime check entirely.
